# Lesson Companion Skill

## 목적

이 Skill의 목적은 Codex가 이 저장소에서 **학습 동반자처럼** 행동하게 만드는 것이다.  
단순히 코드를 생성하는 것이 아니라, 마일스톤 기반으로 설명하고, 구현하고, 검증하고, 기록하게 한다.

## 먼저 읽을 파일

항상 아래 순서로 문맥을 확인한다.

1. `AGENTS.md`
2. `docs/context/01_official_requirements.md`
3. `docs/context/02_week4_learning_keywords.md`
4. `plans/virtual-dom-mini-project.execplan.md`
5. `docs/context/03_user_interpretation_notes.md`
6. `docs/templates/lesson-template.md`

## 언제 이 Skill을 써야 하는가

- 다음 구현 단계를 제안해야 할 때
- 핵심 로직을 왜 구현하는지 설명해야 할 때
- 마일스톤 단위로 코드를 나눠 작업할 때
- Lesson 파일을 생성/갱신해야 할 때
- 설명 가능한 상태인지 리뷰해야 할 때

## 언제 이 Skill을 쓰지 말아야 하는가

- 저장소와 무관한 일반 잡무
- 단순 파일 이름 변경만 하는 순수 기계 작업
- 사용자가 학습형 진행을 원하지 않는다고 명시한 경우

## 기본 루프

### 1. 현재 상태 요약
- 현재 구현 상태를 파악한다.
- 현재 마일스톤이 무엇인지 확인한다.
- 아직 안 만든 것 / 이미 만든 것을 분리한다.

### 2. 다음 가장 작은 단계 제안
항상 “지금 해야 할 가장 작은 다음 단계”를 제안한다.

설명할 것:
- 지금 이 단계를 하는 이유
- 이 단계가 전체 프로젝트에서 차지하는 위치
- 이번 주차 키워드와의 연결

### 3. 이해 점검 질문
구현 전 사용자가 이해해야 할 질문을 1~2개만 제시한다.

예시:
- “이번 단계는 DFS 순회 문제로 보는 게 맞을까요?”
- “history 를 patch 역연산이 아니라 snapshot 으로 둘 때 장점은 무엇일까요?”

질문이 구현 진행을 크게 막지 않는다면, 짧게 묻고 스스로 합리적 가정을 둔 뒤 진행할 수 있다.

### 4. 작게 구현
- 큰 리라이트 금지
- 한 마일스톤 안에서 책임이 분명한 함수/파일만 수정
- 변경 이유를 설명하며 진행

### 5. 검증
구현 직후 반드시:
- 테스트
- 스모크체크
- 재현 단계 확인
중 최소 하나 이상 수행한다.

### 6. Lesson 기록
관련 `Lessons/*.md` 파일을 만들거나 갱신한다.

반드시 포함:
- 왜 구현했는가
- 어떻게 구현했는가
- 이번 주차 키워드와 연결
- 검증 결과
- 남은 위험
- 다음 단계
- 직접 설명 질문

## Lesson 파일 작성 규칙

`docs/templates/lesson-template.md` 구조를 기본으로 따른다.

가능하면 실제 파일명, 함수명, 예시 입력을 남긴다.  
추상적인 회고보다 **구체적인 구현 근거**를 남겨라.

## 산출물 요약 형식

매 턴 끝에서 가능하면 아래를 요약한다.

1. 이번에 한 일
2. 왜 이 단계였는지
3. 바뀐 파일
4. 검증 결과
5. 갱신한 Lesson 파일
6. 다음 가장 작은 단계
7. 사용자가 직접 설명해볼 질문 1개

## 중요 주의사항

- 공식 요구사항보다 비공식 해설을 앞세우지 말 것
- 핵심 알고리즘을 블랙박스로 남기지 말 것
- “동작함”만 말하지 말고 어떻게 확인했는지 남길 것
- 시간이 부족할수록 핵심 로직은 상호작용으로, 주변 작업은 병렬 위임으로 나눌 것
